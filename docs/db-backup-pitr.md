# DB 백업 서버 · PITR 복구

## 왜 만들었나

처음 구성도에는 DB 백업 서버가 있었지만 VM 자원 부담 때문에 구현하지 않은 상태였습니다.
"취약점이 있다"를 보여주는 데서 끝나지 않고 **"공격을 당해도 복구할 수 있다"** 까지 증명하기 위해 직접 구현했습니다.
VM 1대(1vCPU / 1GB)만 추가해 호스트 부담 없이 구현할 수 있었습니다.

## 설계

```
DB 서버(VLAN40) ──SSH(22)만 허용──> 백업 서버(VLAN50)
   매일 03:00  mysqldump(풀백업) → gzip → rsync
   15분마다    binlog 동기화
   백업 서버: 7일 지난 백업 자동 삭제
```

| 항목 | 내용 |
|---|---|
| 네트워크 | 설계만 있던 VLAN50 대역을 구현해 백업 서버 배치 |
| 방화벽 | DB → 백업 방향 SSH 포트만 허용 (최소 권한) |
| 인증 | SSH 키 인증 |
| 권한 제한 | `ForceCommand(rrsync)` 로 rsync 전송 외 동작 불가 |
| 자동화 | cron (풀백업 일 1회, binlog 15분 주기) |
| PITR | MariaDB `log_bin` 활성화 + 풀백업 + binlog 재생 |

### ForceCommand를 쓴 이유

DB 서버가 뚫리면 서버 안의 백업용 SSH 개인키도 탈취될 수 있습니다.
그 키로 백업 서버에 접속해 백업을 지우면 복구가 불가능해집니다.
그래서 백업 서버 쪽에서 해당 키가 **rsync 파일 전송 외에는 아무것도 못 하도록** 제한했습니다.

## 검증

| 테스트 | 기대 | 결과 |
|---|---|---|
| 일반 쉘 접속 시도 | 차단 | `rrsync error` 로 차단 |
| 백업 스크립트 실행 | 정상 | 전송 성공 |
| 방화벽 규칙 | 22번만 도달 | 상태 테이블에서 패킷 매칭 확인 |
| binlog 동기화 | 손실 없이 도착 | 반복 실행 모두 정상 |

## 복구 시연

1. 시나리오: BPFDoor 유형 백도어로 DB 서버에 침투한 공격자가 `invoices` 테이블을 `DROP`
2. 장애 징후: 사이트에 500 에러. WAF가 원본 에러 응답을 한 번 더 막아 "Forbidden" 표시
3. 장애 인지: SIEM(Kibana)에서 `SQLSTATE` 에러 급증 확인. `Table '...invoices' doesn't exist` 로그로 **훼손된 테이블을 정확히 특정**
4. 복구: 백업 서버에서 최신 풀백업을 가져와 복원
5. 확인: 사이트 정상 동작, row 수가 훼손 전과 동일

참고로 이번 시연에서는 풀백업 이후 변경분이 없어 binlog 재생은 하지 않았습니다.
변경분이 있는 경우의 재생 방식은 문서화했습니다. 이때는 `--stop-datetime` 을 공격 직전 시점으로 맞춰 `DROP TABLE` 자체가 재생되지 않도록 해야 합니다.

## 트러블슈팅

| 이슈 | 원인 | 해결 |
|---|---|---|
| MariaDB 재시작 실패 | binlog 저장 디렉터리 없음 | 디렉터리 생성 + 소유권 부여 |
| rsync 경로 중복 | rrsync가 루트 경로를 자동으로 붙이는데 스크립트에도 같은 경로를 지정 | 스크립트 목적지 경로 정리 |
